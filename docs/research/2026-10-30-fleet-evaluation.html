A useful fleet starts with visible ownership

Keep vendor CLI sessions behind ACP. Put durable task intent, dependencies, approvals and artifacts in the home’s coordinator; give the person a project-scoped control surface.

Decision: extend the existing SQLite engine and inspect it before adopting another orchestration runtime. Preserve the default two-slot behavior. Larger opt-in pools should run only across non-overlapping canonical project or worktree roots, reserving a child slot per coordinator and serializing overlapping roots.

Concrete fleet contract

Work and ownership

Task { id, projectId, parentId, dependencyIds, route, status, attempts, maxAttempts, sessionRef, outputRef, errorRef }

Lineage describes who delegated; prerequisites determine admission. A parent waits before its child gets the shared write slot. Keep children direct, bound fan-out, and preserve the selected CLI/model across a conversation.

A cancelled native request can still be finishing. Its workspace and slot stay occupied until it settles; the UI must show that draining state.

Communication and approval

Message { projectId, taskId, sender, recipient, text, idempotencyKey, createdAt, acknowledgedAt }

Accepted mailbox writes are durable records. They do not imply that an agent woke, read the message or accepted new scope. Keep receipts and acknowledgements separate.

Permission replies carry the exact live request and option IDs. Saved permission metadata is inspectable evidence; a lost native RPC cannot be resumed by pretending its promise survived.

Supported control surface

The Fleet panel uses existing APIs: registered projects, paginated tasks and inboxes, full-ID lookup, parent/dependency navigation, requested versus last reported route, attempt/runtime/cost facts, result verification and artifacts. Cancel, retry, permission answers, message sends and new task submission require explicit user actions. API billing starts unchecked; displayed request estimates are admission guards, not a total spend cap.

Polling is bounded to loaded task pages with working or selected tasks; history refresh and additional pages are explicit. The inspector caps loaded task history at 1,000 and inbox history at 250. Messages and artifact text render as text, including untrusted markup. Task instruction/result views and unsent message drafts stay stable during refresh.

Remaining gaps and acceptance gates

  • Human-readable task summaries: task IDs and instruction artifacts exist, but listing titles efficiently needs a bounded server summary rather than fetching every prompt.
  • Durable wait reasons: distinguish dependency wait, permission wait, yielded coordinator, quota wait and process recovery. Derive only what the server can prove; do not invent a paused state from elapsed time.
  • Fairness and admission: test reserved child capacity, overlapping root exclusion, independent-project progress, account limits and cancellation drain before raising defaults.
  • Recovery: exercise crash after dispatch, lost response, duplicate command/message IDs, stale attempt capabilities, missing artifacts and restart with a pending permission. No automatic replay of a whole side-effecting prompt.
  • Outcome evidence: a succeeded turn can still be unverified. Keep declared command/artifact acceptance checks separate from an agent’s own completion claim.

Free scheduler measurement: 36 independent project jobs, three repeats per slot setting, fixed 75 ms mock transport. Mean four-job makespan: 318 ms at two slots, 165 ms at four, 87 ms at eight. One slot per coordinator remains reserved for a child. This measures scheduling throughput, not model speed or cost. Regression tests cover overlapping roots, child capacity and cancellation draining.
